Transport Fever Modder Field Notes

The things the docs don't tell you about modding Transport Fever 2 and 3, learned the hard way.

Building Blueprint Exchange, Pay Your Tolls, Insider Trader and the PYT family meant hundreds of crashes, refused builds and silent failures. Each one was written down with what caused it and what fixed it. This page collects the lessons that apply to any Transport Fever mod: engine rules, fatal assertions with their exact text, and the API calls that really work.

Debugging & reading crashes

The first step after any crash is reading the file that names the real assertion.

The real error is in stdout.txt TF2TF3

The engine writes the native assertion (C++ file, line and condition) to <steam userdata>\<app id>\local\crash_dump\stdout.txt, with older runs in stdout_old.txt or <guid>_stdout.txt. Nothing else contains it. App ids are 1066780 for TF2 and 3493540 for TF3. Count the .dmp files before and after a quit to catch crashes that happen on exit.

Don't trust the thread or mod named in a crash dump TF2

A dump blamed another mod's guiUpdate thread. That was only the thread running when the game aborted. A log line printed by an unrelated mod just before the assertion was a red herring too, and so were bursts of terrain_util::GetHeightAt: pos not valid: (-nan(ind)…). The cause was an assertion further back in an older log rotation.

Why was my build refused? Read errorState TF2TF3

tostring(res) prints only userdata: 0000…. The reasons are in res.resultProposalData.errorState.messages and .critical. What was hit is in collisionInfo.collisionEntities: its entries are records with an .entity field, not bare ids.

A ‘Collision’ can be town houses.

When a road rebuild is refused with “Collision”, look up the colliding entities. If they are town houses (TOWN_BUILDING), the game’s own road tool would demolish them — you can put their constructions in constructionsToRemove of the same proposal, after asking the player. Name what is in the way; ‘the game refused it’ helps nobody. The removal path is untested.

Dry run first: makeProposalData TF2TF3

api.engine.util.proposal.makeProposalData(proposal, context) builds nothing. It returns the costs (era-scaled in TF3), errorState and collisionInfo synchronously, while the async build callback can hide the messages.

  • Critical with 0 messages and 0 entities usually means an invalid reference: a dead node id, or a type lookup that returned "not found".
  • "Construction not possible" is the engine's catch-all. Dry-run each piece on its own to name the culprit. Pieces that pass alone can still fail together.
  • TF3 build 40408: the tealdef declares Proposal, but the game takes a SimpleProposal.

A dry run on top of existing geometry lies TF2

makeProposalData makes every node fresh, with no snapping. An edge ending on a construction it will join reports "Collision", or "Construction not possible" over open grass. A proposal lying exactly on an identical existing piece is judged fine, and the same pieces are then refused elsewhere. To get the game's verdict on a piece, probe it about 400 m to the side, clear of its original.

Listen to the game's own verdict while the player aims TF2

While a construction is being aimed, the placement tool sends builder.proposalCreate to guiHandleEvent, carrying errorState and collisionInfo. Negative collision ids are entities inside the proposal itself (it is colliding with itself); positive ids are real world entities.

builder.apply shows how the game's own tools work TF2

Log guiHandleEvent for builder.apply and you can read the game's recipes. The track upgrade tool, for example, arrives as streetTrackModifier. It re-submits the same pieces in addedSegments, with the same ids and nodes and the new trackEdge.catenary/trackType, and its signals still in comp.objects. It does not delete and rebuild.

Player builds reach guiHandleEvent only after you subscribe TF3

builder.proposalApply arrives only if the script has subscribed to it (LISTEN_ONLY is enough). On the GUI side the param is a list {proposal, data, result}: use param[1]. Ids seen: constructionBuilder, streetTerminalBuilder (a hand-placed signal), streetTrackModifier. Town road rebuilds send no builder event at all, so re-check periodically.

"Thread did not respond to ping" can be the engine, not you TF2

The watchdog fired while mod descriptions were loading, before any script had run. It wasn't a mod bug.

Test pure-Lua modules outside the game TF2TF3

Modules with no game API calls (data, serialisers, geometry) run unmodified in lupa, Python's embedded Lua. Give the harness a global table that refuses new globals to catch strict-global errors offline.

The smoke test must render every page, and stop a commit.

A page called a local helper defined further down: “attempt to call global stockKinds (a nil value)” and a UI reload, while the headless test passed because it never drew that tab. Render every page, forward-declare helpers, and stop the commit chain on a failed test (grep -q "SMOKE OK", not a pipe that still succeeds). Seen.

TF3: print() from a construction script may never reach the log — try debugPrint TF3

Lines written with plain print inside a construction script never showed up in stdout.txt; the same lines through debugPrint did. (A game script’s print does reach the log.) If a construction’s log lines seem to vanish, switch to debugPrint before deciding the code isn’t running.

TF3: what a save load picks up, and what needs a full restart TF3

  • A change to a game script (the .script.lua behind a .gs.lua) was picked up just by loading a save (seen).
  • New files are not indexed until a full restart: a .mdl naming a new sound set logged Referenced sound set not found until the game was restarted (seen). Sound sets and model metadata load at start-up.
  • Loading a save re-read the .con files (a changed availability year took effect), but a changed construction build script seemed to need a full restart (inferred).

When in doubt, restart the game before judging a test.

Game-script edits: a conflicting observation.

In the Blueprint Exchange work, a running game kept the old code after a fix was saved, and a changed .gs.lua (and the scripts it loads) took effect only after a full TF3 restart. "Reload UI" on the error screen re-ran UI scripts only. Data files your script reads each time (a command file in userdata) need no restart, which makes a file-driven dev command channel a fast test loop. If a save load doesn't seem to pick up a game-script change, restart.

TF3: no // in TF3’s Lua — the file never loads TF3

TF3 runs LuaJIT (Lua 5.1 syntax), so the Lua 5.3 floor division // is a syntax error (unexpected symbol near '/'): the construction script failed to compile and the warehouse never built. Write math.floor(a / b). Check syntax with LuaJIT — a 5.3 / 5.4 checker accepts // and won’t warn you. Seen in game.

TF3: ask the game why a line or vehicle has no path — getLineProblems, getVehicleProblems TF3

api.engine.util.line.getLineProblems() returns every line’s problems in one call (the Lines window’s list): { line, type, location }, type being api.type.enum.LineProblem.NO_PATH or BAD_ALTERNATIVE_TERMINAL, location holding nodePosition and okModes / relaxedModes / allowedModes. Pass those three to line_util.getRelaxationType (ug_require "::/gui/line_vehicle_mgmt/line_util.tl") for Catenary / Road / Train / TramLanes / TramTrack, and getRelaxationText(kind) for the game’s own sentence in the player’s language. Seen: “Missing tram lane” at the exact piece.

A line can have a path while its vehicles can’t drive it (electric trams on unwired track): that is a VEHICLE problem — api.engine.util.vehicle.getVehicleProblems() (VehicleProblem.NoPathElectric / NoPathGeneric). For one stuck vehicle, api.engine.util.line.getFailedPathReason(vehicle, line, true) returns a Failure userdata: read f.reason (NoElectric, NoTram, NoTramButTramTrack, NoRail, NoRoad…) and f.pos. Call these on demand, not per frame. Also there: getNoRoadConnectionProblems() and isLineCompatibleWithCarrier(line, carrier, true).

TF3: another mod can wrap your tool and crash it (‘Must not specify more than 1 EdgeRenderable’) TF3FatalInferred

A player’s crash log ended with that fatal on our Select / Paste tool. Another mod wraps the game’s builtin.ActionDescriptor and adds its own EdgeRenderable to every tool whose name starts construction-menu- and doesn’t end -tool; ours already had one. Give your descriptor its own tool = "mymod-tool" name outside that pattern. When a crash shows only for some players, look for mods that wrap base recipes.

A pcall hides a call that doesn’t exist TF3

Minimap vehicle dots never appeared: api.engine.util.getPosition(vehicle) doesn’t exist (it is api.engine.util.vehicle.getPosition(v)), and the pcall swallowed “attempt to call a nil value”. When a pcall-wrapped feature shows nothing, log the error the pcall returns at least once, and check a name exists before relying on it. Seen.

TF2: stamp a code version in your log TF2

TF2 loads a mod’s scripts once per session: a fix saved while the game runs isn’t live until a restart. An hour of tests ran on a session that hadn’t restarted, with three fixes unloaded. Write a version constant into the first log line and into key status messages, so every log says which code produced it. Seen.

TF2: count the arguments in a ‘bad argument’ error’s C++ signature TF2

stack index 3, expected userdata, received table came back unchanged after two fixes aimed at the position argument. The error prints the bound signature — (sol::basic_table_core, ecs::Entity, JournalEntry, const optional<CVec3f>&, sol::this_state) — and argument 3 was the JournalEntry, still a plain Lua table. Build every engine struct (Context, SimpleProposal, ConstructionEntity, JournalEntry) with .new(), then assign fields. When an error repeats word for word after a fix, re-read it. Seen.

TF3: the game's debug overlay shows every lane TF3

Turn it on from the MAIN MENU: Settings > Advanced > Debug Options > Debug Mode. In game the overlay draws the lanes, so you can check that every lane in your construction ends where it should, that stops sit at bay ends, and that there are no dead ends. Use it as a release check for any construction with its own lanes.

TF3: the same crash after every rebuild of ONE construction -- suspect the placed piece first TF3Fatal

FATAL it != components.end() (TransportNetwork, under UI::CSelector) came back after every in-place rebuild of one construction, with the same entity id on every load. Ten crashes and three code theories later, the cause was a DAMAGED placed construction in the save (placed before an update, rebuilt many times). The released version crashed on it too, and a re-placed copy was fine. Bulldoze and re-place it before you rewrite code. Still good practice: read stations a few seconds after a rebuild, not in its callback, behind api.engine.entityExists.

Log what pcall catches, once TF2TF3

An error inside a pcall leaves no trace. One variable-name clash (a number indexed as a table) inside pcall(slowRoadUnder) stopped every speed board for a whole session, with an empty log. Write local ok, err = pcall(f) and print err the first time each distinct error appears.

Threads & Lua states

The game runs your code in several Lua states, and what is legal in each one differs.

game.interface write calls from the GUI thread are fatal TF2Fatal

game.interface.sendScriptEvent called from GUI code died with !gameState.GetGameScriptStack().entries.empty() (cmd_interface.cpp). pcall does not catch it. The same applies to upgradeConstruction, setPlayer and bulldoze. Send an event from the GUI instead and do the work in the game script:

-- GUI side
api.cmd.sendCommand(api.cmd.make.sendScriptEvent("my_script.lua", "my_id", "", { ids = ids }))
-- game script
handleEvent = function(src, id, name, param)
    if src == "my_script.lua" and id == "my_id" then ... end
end

Read-only calls (getEntity, getEntities, getGameTime) are fine from the GUI.

A callback on sendCommand crashes the game at quit TF2Fatal

api.cmd.sendCommand(cmd, callback) hands the engine a Lua function, which it frees at exit after the Lua state is gone. The result is an access violation on every quit, and "Internal error" on an in-game load. It was found by bisection. Where you can, send without a callback, remember what you sent, and check the engine state on a later tick with a timeout.

How the quit crash was bisected.

Every quit crashed at the same address (TransportFever2.exe+0x8cf96, a freed heap block) from ucrtbase’s exit handlers. One config flag per relaunch found it: toolbar button off — still crashed; no money command — first clean quit. A heartbeat probe showed the mod’s update never runs during teardown, so nothing can tidy up at quit. Send without a callback and read results back on a later scan. Seen.

update() doesn't run while the game is paused TF2

Work queued for the game script's update() never ran on a paused map. Do event-triggered engine work directly inside handleEvent. Background schedules belong in the game script's guiUpdate/update with your own throttles, never in code that only runs while a window is open.

TF3: one Lua state per sim thread TF3

On the engine side, update() runs on many "Sim Pool" threads, each with its own Lua state, so module-level locals are per thread: a "run once" flag ran 22 times. Keep engine-side state in the game script's state, which TF3 saves inside the savegame.

TF3: what exists where TF3

  • app is GUI-side only. On the engine side: attempt to index global 'app' (a boolean value).
  • io is nil on both sides. os is a table, and require/ug_require exist.
  • The GUI reads the engine state read-only and changes it only with api.cmd.makeScriptingSendEventCmd("", "<ns>", name, param).
  • Any content/**/X.gs.lua becomes a game script with no registration (log: Creating entity for GameScript …).

TF3: a plain-Lua game script must return its table from data() TF3

A .script.tl (Teal) game script ends with return ret. A .script.lua one must wrap it: function data() return ret end, the same way construction scripts do. With a bare return, stdout.txt fills with "Error while running game script … Expected table at path: game <mod>::/<file>.script", from every Sim Pool, on every step. Those errors can also upset other things the engine is doing. (We earlier guessed plain-Lua game scripts don't run at all; this was the cause.) A game script change is picked up by loading a save, without a full restart.

TF3: subscribe to events on the start-up events TF3

Call state:subscribeToEvent inside handleEvent on the start-up events (id "" with initNewGame / handleLegacy / initNewGameFromMap), as the base company script does. A mod added to an existing save does get handleLegacy. An old save's subscriptions don't cover events added in a later mod version, so track which ones the save has and subscribe the missing ones.

Component params are an engine wrapper, not a table TF2

api.engine.getComponent(id, CONSTRUCTION).params refused edits with cannot call erase on lua::Table. game.interface.getEntity(id).params is a plain Lua table you can copy and change.

Strict globals and declaration order TF2

Assigning an undeclared global fails with res/scripts/init.lua:130: creating globals by assignment is not allowed. That usually means a file-level local was declared below the function that uses it. Likewise, a local function defined below its caller is nil at the call: attempt to call global '…' (a nil value).

TF3: a game script’s GUI hook is its own Lua world TF3

Window scripts share one Lua state (and one string.* table, which is how mods can share data). A game script’s guiUpdate hook is not part of it: figures two game scripts put on a string.* field never reached a window script. What worked: keep the figures in the game script’s saved state and read api.engine.getComponent(gameScriptSystem.getEntityForGameScript("<modId>::/x.gs"), GAME_SCRIPT).state from the window — an expensive read (see Performance). Seen in game.

TF3: ‘Missing builtin recipeId’ means a game script loaded window code TF3

A shared module did ug_require "::/gui/main/react.lua" (and other UI helpers) at file level, and game scripts — which also run on the simulation threads, with no window toolkit — required it: the log filled with “Missing builtin recipeId” (24 in one session). Fetch UI modules lazily, inside a function that only runs when something is drawn, and keep any file game scripts may load free of window code at top level. Seen in game.

TF3: a game script’s GUI side runs only if guiUpdateScript is registered TF3

A .gs.lua’s data() lists each entry point: updateScript, handleEventScript, guiHandleEventScript, guiUpdateScript, each { fileName = "mymod_1::/folder/file.script@functionName" }. Leaving out guiUpdateScript meant nothing on the GUI side ran — no error, no log line. If GUI-side code seems dead, check this list first. Seen.

TF2: handleEvent and guiUpdate don’t share module state TF2

tostring(stateTable) printed different addresses from the two callbacks: a hub chosen in the GUI was never seen by the event code, so auto-dispatch never fired once in 12,700 deliveries. A module that caches a file once caches it per instance. Hand state across through a file and re-read it, or keep the work in one callback. Seen.

TF2: never send commands from inside a simulation event TF2Fatal

handleEvent for SimCargoSystem / OnToArriveAtDestination runs inside the engine’s own delivery processing: api.cmd.sendCommand from there failed 45 of 45 times, with ecs::Engine::BeginModification(): !m_betweenChanges; the same calls from a button click worked 10 of 10. A retry loop wrote 1,397 crash dump entries within a minute. Let the event set a flag and send from guiUpdate; cap attempts. (A script event you send yourself is safe to act on.) Seen.

TF3: no event announces new lines, stops or vehicles -- poll slowly TF3

None of the base scripts' subscribeToEvent uses reports a line created or changed, a stop added, or a vehicle bought. A popular terminal-assigning mod sweeps on a timer too. Poll from the engine-side script: lineSystem.getLinesForPlayer(api.engine.util.getPlayer()), skip unchanged lines by a per-line signature, and run rarely. Every 30 s of real time, with jobs taking turns, was enough.

An engine callback that never returns: give busy a watchdog TF3Inferred

If your tool sets busy = true while a sendCommand callback is pending, one lost callback leaves the mod dead until a restart. Drop busy after about 3,600 frames (~60 s) and log it. Also guard every delayed callback: the window it updates may be gone by the time it fires. Move It's 2026-10-05 update fixed exactly that.

Files, saves & persistence

TF2: data() save/load hooks crashed when used for mod state TF2Fatal

The game script's save/load functions exist, and base scripts use them, but eight attempts to keep mod state in them crashed. The engine calls load() more than once inside CGame::StartGameSim (Game.cpp:330) and asserts that the saved outputs match. Plain io.open files survived quit and relaunch, so that is the route.

TF2 file sandbox: what works TF2

  • io.open works in the game script, the loader state and a .con updateFn. Paths resolve from the game exe folder (steamapps/common/Transport Fever 2); relative paths like ../../workshop/… work.
  • os.rename and os.remove silently do nothing. To "delete", overwrite the file with a one-line tombstone. To rotate, copy by read and write into a fixed ring of slots.
  • There is no directory listing.
  • loadstring/setfenv were missing in a .con updateFn; parse plain text with string.gmatch. Elsewhere, run untrusted data files under setfenv(chunk, {}).
  • The engine-thread game script could not write the mod's log file, but its print() reaches stdout.txt.

Your files are global, not per save, so key them per map TF2

The TF2 API exposes no save or map id, and a new game inherited stale data from another save. A fix that works: hash the sorted set of town id=name pairs (fixed for a map) into the file name, for example djb2 to 8 hex digits. Files can also run ahead of a save reloaded without saving, so record the last game date written and roll back when the loaded save is older.

TF2: a stale id from another save crashes deleteLine.

Two saves of one lineage share entity ids, so a file beside the game made a fresh save look ‘already managed’; cleaning up called api.cmd.make.deleteLine on a line id from the other save — a native “Internal error” pcall can’t catch. Re-check every stored id right before any destructive command, and allow one setup sequence at a time. Seen.

The first ticks after a load can see no towns TF2Inferred

Gate loading on a readiness check. Never prune or overwrite saved data against an empty town list in the first ticks.

TF3 userdata: app.saveUserdata and friends TF3

app.saveUserdata / loadUserdata / getAllUserdata / removeUserdata work on the GUI side only. Files land in …\3493540\local\<dir>\ as function data() return {…} end. Sparse integer keys are dropped, so store lists of pairs. Check getAllUserdata before loading to avoid log errors. Engine-side state lives in the game script's state, inside the savegame.

Never wrap a save in a silent pcall. On build 40420 one mod's app.saveUserdata("pay_your_tolls", …) threw "The directory you trying to access is not available or invalid", while another mod's "bpxdata" folder kept saving. The pcall hid it for days, and the player's "Don't show again" never stuck. Log the error. The cause (a folder-name rule?) is still unconfirmed; short folder names without underscores have kept working. Update: "bpxdata" was refused too once the game restarted. Since 40420 every folder a mod made is refused (save, load, list, remove); the game's own "mod_presets" (and "heightmaps") still work, so save there with a file-name prefix of your own.

Use "heightmaps", not "mod_presets". Every .lua in mod_presets shows in the game's Load Preset menu, with a delete button: BPX's 30 working files filled a player's preset list. The map editor's heightmap list (app.getAllHeightmaps) ignores .lua files, and its .lua list reads towns_industries, so heightmaps shows in no player list. Subfolders (mod_presets/x, heightmaps/x) and other extensions don't help: a subfolder is refused, and a name like x.bpx is saved as x.bpx.lua.

A construction that rebuilds in place must OWN its roads. A road piece in a construction's edgeLists belongs to the construction only if it touches a fixed node, one listed in neither snapNodes nor freeNodes. Mark every node free and the roads become ordinary public roads once built. A later createProposalReplaceConstruction then adds a fresh set on top and removes none: "Construction Not Possible", even with ignoreErrors = true. So make only the outer ends snap nodes and leave the rest fixed. Node tags ({ pos, tangent, tag }, ends with one tag join even metres apart) work on owned roads, as the base cloverleaf shows. (PYT Harbour City: its plaza's speed, lamps and town name only rebuilt once it owned its roads.)

A road stop as a module on the vanilla train station (PYT - Interchange's Truck Bay, seen working in TF3 40420: a truck loads at the train station itself). What it took:

  • Inside a mod, every base-game path needs ::: require "::/scripts/mat4.tl", and models, textures and street types too. Without it the game looks in your own mod, and a missing model crashed the module builder.
  • Keep a module's STREET edges inside its own slot. The builder tries neighbouring slots too, and two modules' road ends on one spot is a fatal nodeInfo.edgeCount == 1 in GetNodes2snap. Only the outer ends go in snapNodes (indices count the {pos, tangent} entries).
  • Don't push your stop into the train station's own stop list: that crashed the engine. Wrap result.terminateConstructionHook, call the original, then append your OWN station subconstruction ({ models = {}, laneLists = {...}, station = {...}, tag = n }). It is one station group with the trains, and the window shows it as a Road Station tab.
  • Build the lanes with laneutil.createLane (two-point curves are fine). The truck lane needs TWO pieces with the stop on the middle node (vehicleNode = {0, 2}, vehicleEdges = {{0,0},{0,1}}). A stop on a lane's end node is a fatal findBestDepotForLine (s)>=(1) when buying a vehicle.
  • The stop needs tag, vehicleEdges and cargoTransferSpeeds (with a cargo class), or the station window's TerminalTitle fails with "argument #2 can't be cast".
  • Make it 20 m long: at 10 m the warning is "Terminal is too short for some vehicles" and nothing loads. For catchment, copy the train station's catchmentAreas in, or the stop reports "not functional".
  • addModel in a module already applies the module's transform, so pass local transforms, not world ones.

Open a folder in the player's file explorer: app.openUserDataSubFolder("mod_presets") and app.openUserDataFolder() (the game's local folder) work from a GUI button (seen on Windows, 40420). Like saving, the sub-folder version opens nothing for a mod-made folder, so send players to local for those. Mac/Linux untested.

TF3 translations: strings.json TF3

TF3 reads strings.json in the mod root: { "ru": { "English text": "translation" } }, for the 13 game languages. TF2-style strings.lua and .mo files are not read. The game language is api.util.getLanguage().code. For a language the game lacks, carry your own table and look it up yourself.

Three translator traps.

  • for _, x in ipairs(t) shadows the translator inside the loop: attempt to call local _ (a number value).
  • _G["_"] is the game’s global translator and never sees your strings.json (442 Russian texts never showed).
  • The script’s own _ works out the mod from its caller; called through pcall the caller is the engine, so it throws Value is not a string, but a nil with a logged stack trace every call — stutter at every window, a crash on exit.

What works: generate a Lua table from strings.json at build time, ug_require it, and pick the language from api.util.getLanguage().code. string.lower doesn’t fold Cyrillic. Seen.

Language keys are the game's folder names; a language-pack mod adds one.

strings.json sections are keyed by the folder names in base/strings (de, fr, ru, pt_BR...). A language-pack mod can add a whole new game language. The Ukrainian pack (mod.io 6415498) ships content/locale/uk.lang.lua with Cyrillic fonts and strings/uk/LC_MESSAGES/base.mo. That makes its key uk: add a "uk" section and players with the pack see it, while everyone else never reads it. No dependency needed. New strings may need a full restart to show.

TF3: a script copy can find its own mod; another mod can be detected TF3

debug.getinfo(1, "S").source gives "<modId>::/path" in UI scripts, so a file shipped byte-identical in several mods knows which copy it is. api.res.constructionRep.find("<modId>::/<path>.con") on another mod's key entry tells you whether that mod is installed.

List installed mods, tell which are on, read another mod’s file.

  • app.getUserProfile():getModRep():getInstalledMods() lists every installed mod, on or off: .name (the mod id), a display name via getGameModDesc(id).name, its source and mod.io id. Seen: 45 mods.
  • ug_require("<modId>::/folder/index.lua") reads another mod’s file; a missing file fails quietly; a staging mod switched OFF is still readable (seen).
  • Which mods are on in this game: the keys of api.engine.config.getModParams() — every active mod appears, as { } without params (from the log; not yet used in code).

Detect installed modules with moduleRep.

A pack that ships only modules has no .con to probe. api.res.moduleRep.getAll() lists every loaded module: count the names with your prefix once per session. If the list can't be read, treat the pack as absent.

Entity ids are reused TF2TF3

A record keyed by id alone matched a quarry that had taken an old town's id ("% Owned 9434.40%"). An undo "new since my snapshot" diff picked up four of the player's rebuilt track pieces. Never cache "what this id is" across passes. Store the type, and the position where it stood, with the id, and re-check both before acting.

TF3: a vehicle’s own sound set (.snd.lua) TF3

In the base zips a .snd is the file x.snd.lua: plain Lua — soundsetutil.makeSoundSet(), then one soundsetutil.addTrackParam01(data, wav, reach_m, volumeCurve, pitchCurve, {"vehicle","speed01"|"power01"}) per layer, and addEvent(data, "horn", {wavs}). WAV paths are relative to the .snd.lua’s folder; the base helicopter WAVs are 48 kHz, mono, 16-bit.

The .mdl names the set without .lua: soundConfig.soundSet.name = "mymod_1::/my_sound/my.snd". A copied base set’s first line must become require "::/scripts/soundsetutil.lua"; as copied, the require fails and the whole set is dropped (Referenced sound set not found). To lower the volume, halve each track’s first curve — addEvent has no gain. Seen in game.

TF3: keep every file path lower case TF3

The Validation Report warns once per file: “File path contains uppercase characters, but lowercase is recommended” — 23 warnings for one Model Editor folder (PYT_toll_sign/) plus a picture named flag_pt_BR. TF3: left-hand traffic -- how to tell, and what it flips TF3

TF3 itself only drives on the right; the Left Hand Traffic mod flips it as the game loads (a loadStreetTemplate modifier on every street type, other mods' too): each two-way road type's traffic lanes get forward reversed (and busAndTramRight = false); one-way road types keep their direction; station / depot / industry / warehouse interiors are converted after the construction pipeline. So a cheap test anywhere api.res works: country_new_medium's lane 2 (its first traffic lane; lane 1 is the pavement) has forward == false on a right-hand game and true once flipped. You can write a TF3 model without the Model Editor TF3

An imported model is just <name>.mdl plus, per part, msh\<part>_lod<n>.msh (a short text header) and a binary .msh.blob.

  • The .blob: de-duplicated float32 value streams (position xyz, uv0, normal xyz, tangent xyz + bitangent sign), then one uint32 index stream per attribute, three per triangle.
  • The header: each attribute's count and byte offset, keys in alphabetical order.
  • Mesh space is Y-up: Blender (x, y, z) becomes (x, −z, y). Each .mdl node carries the transf the editor writes: { 1,0,0,0, 0,-1.62921e-07,-1,0, 0,1,-1.62921e-07,0, 0,0,0,1 }.

A writer built from this matched the editor's output (one test mesh decoded identical; elsewhere only the quad diagonal and tangent averaging differed), and its models work in game. It's also the way to update a model in place, which the editor won't do.

.msh header counts are bytes.

Both count and offset in a .msh header are byte counts (checked on a shipped file: last offset + count = the .msh.blob size). Indices are uint32, three per triangle, so triangles = indices.position.count / 12. An audit that read counts as index counts reported every model 4× too heavy.

The Model Editor won't overwrite an existing model TF3

Importing under a name that already exists doesn't replace the model. Either save the new version under a new name and repoint the .con, or rewrite the model's files directly (above). Delete old model folders only with TF3 and the editor closed.

How to work

These habits did more than any single trick.

Never invent an API call; prove it first TF2TF3

Read the base game's own scripts and well-used mods (Advanced Statistics, AI Builder, Copy It, Move It, Automatic Signal Spacing) to learn the real calls and which thread they run on. TF3 ships its API as Teal definitions in api/tealdef. Build a throwaway in-game probe and record the result, positive or negative. Save before any probe that writes game state, because native assertions can't be caught.

Keep a decision log, and say what was seen TF2TF3

Every change gets a numbered entry: what, why, and "not yet seen in game" until it is. When something breaks three times in one function, that log shows the pattern. It's also where this page came from.

Render it from the player's side before import TF2TF3

Render each model from where the player will see it: the drivers' side for anything facing traffic, at night for anything that glows. One pass caught 12 gantries built facing away from their drivers before any import.

Read the log before guessing TF2TF3

Give your mod its own log with a clear line for every step that matters, and a diagnostic line when something comes back empty. More than once the fix was obvious from one log line, for example asset-group ids coming back as 1, 2, 3.

Same file in two mods: a tab merges, a construction doesn't TF3

Several mods can each ship the same menu tab (menu_categories/*.res.lua, same category id) and the game shows one tab. A construction is different. A .con at the same path in two mods becomes two separate entries (modA::/x.con and modB::/x.con), so shared buttons show twice. To share buttons between mods without a common dependency, let each mod register itself in its runFn (all of them run before any construction loads). Pick one owner deterministically, for example the first mod id alphabetically. Then hide the other copies from a loadConstruction modifier. Have each mod decide only for its own copy, so a failure shows a duplicate rather than nothing.

Sharing state between mods without "Global variable in mod" errors (and without rawset) TF3

Mods' scripts run in one Lua state, so a plain global (MY_FLAG = true) works as a shared flag between mods. But TF3's base/init.lua guards _G: every new global a mod creates logs ERROR Global variable in mod with the mod id and key. One flag set in a runFn showed up 199 times a session, once per loading thread. Don't reach for rawset: TF3's mod environment has no rawget or rawset, so calling them is a fatal "attempt to call global 'rawget' (a nil value)" in your runScript. Instead, hang ONE shared table on an object that already exists, such as the standard string library: local t = string.my_shared; if t == nil then t = {}; string.my_shared = t end. That's a field, not a new global, so nothing is logged, and every mod in the same Lua state reads and writes the same table.

Several mods shipping one shared core: let the newest copy act.

When several mods each ship a copy of the same shared script, a player may update one and not another. Have each copy write its version into the shared table as it loads and run only if it is the highest seen; older copies stand back.

A hover menu in the top bar, and mods joining each other's buttons TF3

A builtin.Button in the mod button area (top left, main_mod_button_area) can react to the mouse: put onMouseOver = function(hover) ... end inside its meta, as the base game's line manager does. It gets true when the mouse arrives and false when it leaves. Moving along a row of buttons fires OUT of one and IN to the next in the same frame, so a counter (react.useRef, +1 on IN, -1 on OUT, close at 0) keeps a fold-out row open with no timer. Mods' GUI scripts share the same string table too (seen 2026-10-12): one mod can put { label, icon, open = function } on string.my_family at load, and another mod's toolbar can draw a button for it and call open, with no global and no dependency between the two.

Key handlers live in the tab's tiles -- pick one to act.

react.useInputAction handlers in construction_tool recipes run only while that build-menu tab is open. Every tile in the tab registers them, so one press reached several tiles: let exactly one act. With the tab closed, a tool still on screen heard no keys. A shared clock (0.15 s) makes each press count once.

Live text on a model: a town's name and population on a sign TF3

A model can carry text the game draws for you. In the .mdl, put metadata = { labelList = { labels = { ... } } }. Each label has type = "CUSTOM", a size = { w, h } in metres, a color, an optional fitting = "SCALE" (long names shrink to fit) and renderMode = "STD" or "EMISSIVE". Its transf puts the label's bottom-left corner on the surface, with x along the text, y up and z out of the face. Keep it about 1 cm proud: 2 mm can flicker, and 4 cm can vanish. The construction's updateFn fills the labels per model with sub.labelText = { [0] = { "BARNES", "POP. 672" } }: index 0 is the subconstruction's first model, and the strings go to its labels in order. For the data, a GUI-side script finds the nearest town with api.engine.system.streetConnectorSystem.getConstructionClosestTown(entity) and its name with api.engine.util.getEntityName(town). Population is the town's residential capacity, api.engine.util.town.getTownCapacityUsage(town)[api.type.enum.LandUseType.RESIDENTIAL + 1].capacity, the same number the town statistics show. The script then rebuilds the construction with those strings in its params (createProposalReplaceConstruction), only when they change. Two warnings: a Model Editor import rebuilds the .mdl and drops the labelList, so add it with a script you can re-run. If metadata already holds a lightSourceList (lamps), add to it rather than replacing the block, or the lights go dark. Seen working 2026-10-12: "WELCOME TO BARNES / POP. 672".

The Lua trap: x and nil or y is always y TF2TF3

Lua's a and b or c only works as a one-line if when b can't be nil or false. st.counting = (on == 1) and nil or 0 reads like "nil when on, else 0", but nil counts as false, so the or always wins and it is always 0. In PYT 2.6's test that meant a decoration switch that could be turned Off and never back On. When one branch is nil or false, write a plain if ... then ... else ... end.

"The native floating point can't fit inside a lua number" = you passed NaN TF3

This crash (a hard Lua error box, the game closes) comes from handing the game a number that is NaN or infinite, for example into api.type.Vec3f.new for a road's position or tangent. The message never says NaN. The usual cause is a divide by a length that can be 0: two points on the same spot, or a zero-length tangent you normalise. Guard every such division (if len > 0.01), and pass every number you build geometry from through a check before it reaches the game: if v ~= v or v == math.huge or v == -math.huge then v = 0 end (v ~= v is only true for NaN). Seen 2026-10-12 in Blueprint Exchange's paste.

Match file names by path, never by a bare name TF2TF3

A construction's fileName carries its mod prefix, for example epod_pyt_harbour_city_1::/pyt_pack/pyt_pack_sign.con. Searching it for a bare word like "pyt_harbour_city" to find one particular construction matches every file in that mod. A "nearest toll" search took each roadside sign for a toll 0 m away (itself), so no sign ever turned. Search for the folder and file together ("/pyt_harbour_city", "pyt_plaza/pyt_harbour_city"). Also ignore anything within a few metres of the thing doing the search.

Hearing the player's builds: subscribe, and remember it yourself TF3

A game script's guiHandleEvent only receives builder.proposalApply after the game side has called state:subscribeToEvent("builder.proposalApply"). Do it in update as well as on the start-up events, because a mod added to an existing save doesn't see those. Don't guard it with state:hasEventSubscriptions(): that can already be true, so the call is skipped and the instant reaction never comes. Keep your own "subscribed" flag in the script's state instead. The entities just built are in param[3].

Town road works never reach guiHandleEvent.

Only the player's builds arrive as builder.proposalApply. When a town rebuilt a street into a wide tram avenue, no event came, and a snapped gantry kept its old size with a post standing in the road. Re-check road-dependent pieces in a periodic pass too. Also: building a new road through a decoration removes it, but widening an existing road leaves the decoration standing in the new lanes.

Place roadside signs from the road's measured edges, not by turning TF3

A one-armed sign took many rounds of "turn it 180 degrees" before it sat right. Three things fixed it. First, read the model itself: a .msh.blob holds float32 positions at offset × 4, and our sign's origin turned out to be under the board, with the pole 2.55 m to one side. Second, if your script turns the whole construction to face its traffic, the road can be on either side of the sign's local frame, so any fixed turn is right on one road and wrong on the next. Third, one rule from the road's real width (the base edge's lane widths, pavements included) puts every sign a set distance outside its own edge, which balances both sides.

A window can't tell when the mouse leaves it: onMouseEvent only fires while the mouse is over it TF3

We wanted the Minimap to hide its buttons when the mouse is away. A react.onMouseEvent on the window's body does get its children's events (they bubble up; evt.handled says a child already took it), but only while the mouse is over the window. Every event we logged was inside it, and leaving it sent nothing: the Exited events all came from moving between child elements, at a position still inside. What works: treat "a mouse event in the last ~1.5 s" as "over", counted in react.onStep (about 90 steps). 2026-10-22, PYT Minimap.

Steering lanes through a junction: write the node's laneConnections yourself TF3Inferred

Read in a third-party road mod (Roadform's turbo roundabout), not yet tried by us. The engine picks which lane feeds which lane at a junction, but a script can overrule it. Read the node's BASE_NODE_CONFIG and clone() it. Fill comp.laneConnections with api.type.LaneConnection.new() records (segment0/lane0 = the edge and lane coming in, segment1/lane1 = going out, withRoad = true, withTram = false). Send it as streetProposal.nodeConfigsToAdd (a BaseNodeLaneConnectionAndEntity) with the node also in nodeConfigsToRemove. The lane index is the edge's laneConfigs index (0-based) counted from the end the node is at: from node0 it is the index, from node1 it is #laneConfigs - 1 - index. Only the CAR+BUS lanes are counted when choosing a lane by its place. The mod keeps the old config to build a restore proposal, sends with context.cleanupStreetGraph = false so the nodes survive, and reads the config back after the callback to check the links really landed.

A script can post a game notification; a dry run before every proposal; tagged construction road ends TF3Inferred

Also read in Roadform, not yet tried by us. Notifications: api.cmd.sendCommand(api.cmd.makeScriptingSendEventCmd("", "Notifications", "add", { type = "<mod>::/game_mechanics/x/my_note.script", params = {...}, autoDismissDuration = 60000 })) pops a message in the game's notification list. It needs a .res.lua ({ type = "notification", data = { guiType = "Problem", label = ..., initiallyIgnoredType = false } }) and a .script.lua whose useDataState(params) returns { title, description, icon }. Dry run: before makeWorldBuildProposalCmd, pcall(api.engine.util.proposal.makeProposalData, proposal, context) and don't send when pd.errorState.critical. Native lists: when pairs() fails on an engine collection, pairs_native(t) walks it. Construction roads: each edgeLists end can carry a third field, a tag string ({ pos, tangent, "n12" }). Ends with the same tag become one node even when they lie a little apart, and an untagged end never merges with a tagged one. With every end in freeNodes the roads stay as ordinary streets. To stop the game's clean-up merging short pieces into one curve, the mod uses a hidden copy of a street template (empty menuCategory, simBuildable = false) for the middle piece.

The sandbox mod is one flag; an industry's road comes from its construction, and the engine never links it to the network TF3

Wanting to learn how the game places an industry "with a road attached", we read the sandbox mod that ships with TF3 (mods/release/urbangames_sandbox). It is eight lines: preRunFn sets baseConfig.sandboxMode = true, and everything else is the engine. The road comes from the industry itself: industries/industryutil.lua adds the entrance stub and a short country-road "street cross" to the construction (constructionutil.addEdges(data.curves.street, ..., "STREET", ind_entrance_*, snap node {0})). The engine offers a complete proposal through api.engine.util.proposal.makeIndustrySpawnProposal(typeTag, town), which the game's own prospection sends as it is. We dumped one for a coal mine: 16 nodes and 14 segments added, none removed. It holds the construction's pieces plus two straight road pieces across the entrance (tangent = chord), and it does not split or join any road already on the map. The join to the network is left to town growth, to the player, or, in sandbox, to the construction tool's snap, which is C++. So a mod that wants a pasted road to T into a map road still has to cut that road itself (remove the piece, add two halves and a node, remap the lane tables at its far ends). One format detail worth copying: the engine adds a lane table for every new node, an empty one for each dead end. Also found while looking: api.engine.util.proposal.checkProposalConnectsNodes(startNode, startEdge, targetNode, streetProposal, isApply) reports whether a street proposal joins two nodes, a ready-made connectivity check.

Moving an industry: rebuild it in place, build its roads, then refresh it once more TF3

An industry moved with the in-place rebuild (remove + add + old2new, the same entity, stock and name kept) comes back with a fresh entrance junction, but the road you then build onto that junction stays a dead end: a no-entry sign at the junction, and no route through it. The engine laid the junction's lane table when it rebuilt the industry, before your road existed, and adding a segment to a node does not relay it. Two things do not help. Rebuilding your own piece with api.engine.util.proposal.replaceSegment succeeds and changes nothing. Rebuilding the industry's own entrance piece the same way hangs the game: a construction's edges are frozen, and the call never returns, with no error in the log. And rebuilding a piece the same paste just built at that junction is fatal: TransportNetworkSystem::EntityToBeRemoved asserts AreAllNodesEmpty, because the new piece's network nodes are already in use. replaceSegment is for a piece the map already had, with your new piece beside it. What works is what a road station needs after its road arrives: api.engine.util.proposal.refreshConstruction(entity), sent with makeWorldBuildProposalCmd after the roads are built. TF3: a wrong-side stop on a line that works — measure, don't just route TF3

api.engine.util.pathfinding.findPathNodeToNode({a},{b},{mode}) finds ANY route, however long, so ‘is there a path’ passes a stop on the far side of the road whenever the town's streets or track let the vehicle loop round. Sum the route's road pieces (each BASE_EDGE once) and compare: the stretch in from the stop before plus out to the stop after, for each bay. When many stops are wrong, judging one stop against its (also wrong) neighbours fails — plan the whole line at once (every stretch for every pair of bays, shortest round trip). Then a stretch still 3× the straight-line distance is the vehicle driving round the block to turn. A stop's bays: every terminal of every station in its STATION_GROUP; the line stop names them by station and terminal (0-based). Seen 2026-10-28 in PYT - Tram Doctor on Epod's test lines.

TF3: rebuilding road pieces — never drop a junction's node config, remap it TF3Fatal

A street proposal that rebuilt pieces and put their end nodes in nodeConfigsToRemove without adding configs back (hoping the game would make fresh ones) passed makeProposalData, was accepted — and then the simulation thread died: ecs::Engine::GetComponentDataIndex: Assertion 'it != components.end()' failed on two entities, just after transition not valid: entity ..., type class StreetGeometry::Crossing.
